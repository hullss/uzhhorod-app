# Готовність «Ужгород Цифровий» до презентації

> Це знімок перевірки від 20.10.2026 до наступних доробок. Актуальні виправлення та межі перевірок описані в [PRESENTATION_FIXES_2026-10-20.md](PRESENTATION_FIXES_2026-10-20.md) і [AUDIT_FOLLOWUP_2026-10-21.md](AUDIT_FOLLOWUP_2026-10-21.md). Зокрема, виправлені дані безбар’єрності, читач новин, головна, дії ЦНАП, невідомий статус тривоги, checked-стани вебналаштувань і перегляд розкладу; опубліковане адресне доповнення укриттів.

Дата перевірки: **20 жовтня 2026 року**. Аудиторія за робочим припущенням — міська рада / IT-кластер; живий показ на телефоні на 5–7 хвилин. Аналіз охоплює поточне робоче дерево, включно з наявними незакоміченими змінами профілю.

## Висновок

**Проєкт уже можна показувати як змістовний незалежний прототип, але показ усіх сервісів без попередньої репетиції ще ризикований.** Реальні транспорт, GPS, новини й валюти поєднані із завершеними локальними сценаріями паркування та ЦНАП. Це достатня основа для переконливої зустрічі. Найсильніший показ — три пов’язані історії, кожна з видимим результатом.

Перед показом із браузера обов’язково усунути проблему підкладки транспортної карти: у живій перевірці замість вулиць відображалися великі плитки **«403 Access blocked»**, хоча автобуси й геометрія маршруту працювали. Перед показом із телефона окремо перевірити саме нативну збірку: браузерна перевірка не підтверджує її готовність.

Наступні важливі доробки: виправити читання актуальної схеми безбар’єрності, очистити читач новин від десятків однакових посилань на фото, поліпшити перший екран і підготувати актуальний контент. Підключати справжні платежі перед цією зустріччю недоцільно.

**Готовність до презентації: 7/10. Готовність до публічного пілота: 4/10.** Це експертні оцінки за критеріями нижче, а не виміряний відсоток завершеності.

| Критерій | Презентація | Пояснення |
| --- | --- | --- |
| Завершені користувацькі сценарії | 8/10 | Є реальні дані й локальні операції зі збереженим результатом |
| Візуальна цілісність | 8/10 | Профіль, налаштування й форми виглядають узгоджено; перевірено вебверсію на 390 і 320 px |
| Якість і пояснення даних | 6/10 | Є контроль застарілості, але схема безбар’єрності відстала, адрес укриттів немає |
| Передбачуваність живого показу | 6/10 | Є зовнішні залежності й підтверджений збій вебпідкладки карти |
| Технічна перевіреність | 7/10 | Перевірки проходять; фізичний телефон, камера й нативна доступність не перевірені |

Впевненість у висновках про API та відтворені вебсценарії — висока; у перенесенні візуальних результатів на iOS/Android — середня; у готовності до пілота під навантаженням — обмежена. Для пілота потрібні перевірені пристрої, експлуатаційне середовище, підтримка, робота з акаунтами та погоджений обсяг офіційних інтеграцій.

## 1. Десять найважливіших висновків

1. **Транспорт — найсильніший доказ працездатності.** Справжній GTFS імпортувався в тимчасову БД: 18 маршрутів, 217 зупинок, 40 варіантів напрямків, 658 зв’язків маршрутів із зупинками. Для №7 API повернув 7 автобусів; у UI відкрилися маршрут, карта та планові відправлення.
2. **Вебпідкладка транспортної карти може зіпсувати весь показ.** Автобуси накладаються на зображення блокування OSM. Це конкретний відтворений дефект демонстрації, а не загальне побажання щодо дизайну.
3. **Паркування вже є завершеним локальним прототипом.** Пройдено майданчик → авто → тривалість → тестовий спосіб оплати → підтвердження → активна сесія. Після перезавантаження сесія відновилася. Підкладка OpenFreeMap працювала, коли тестовий сервер правильно обслуговував локальний worker.
4. **Старі критичні зауваження не слід механічно повторювати.** Поточні перевірки підтверджують захист історії квитків від перезапису після помилки, збереження каталогу при завеликій геометрії, унікальні нативні маркери кільцевих маршрутів та оновлення вебкарти без її перебудови.
5. **Безбар’єрність потребує виправлення контракту даних.** Джерело вже використовує `uid` і `monitoringDate`; парсер читає `buildingId` і `date`. В API всі 78 записів втрачають дату моніторингу, а адресні компоненти збираються в неправильному порядку. Літеральне `null` від сервера UI прибирає, тому воно не було видимим на перевіреному екрані.
6. **Каталог відкритих даних через застосунок зараз зламаний.** Прямий запит до міста успішний, серверний endpoint повертає 503 через upstream 400 «Invalid sort parameter». До того ж клієнтська функція каталогу не підключена до видимого екрана.
7. **Поточний шар укриттів не дає повноцінного адресного сервісу.** Адаптер повернув 333 точки: у всіх замість адреси повідомлення про її відсутність, жодна не має `verifiedAt`. Список і пошук у коді є, але пошук за вулицею без адрес не вирішує задачу користувача.
8. **Читач новин працює, але потребує редакційного очищення.** Актуальна стаття відкрилася з повним текстом і фото; після тексту API додав 34 посилання з однаковою назвою «Відкрити посилання» — це посилання на фотографії галереї.
9. **Профіль і налаштування вже виглядають якісно.** На 320 px англійські назви нормально переносяться, лічильник записів ЦНАП оновлюється. Повний редизайн цих екранів зараз не потрібний.
10. **«Вау» варто будувати на наявній основі.** Найкращі кандидати — швидкий доступ до свого маршруту, невелика прогулянка серед 21 уже наявної мініскульптури й новий перевірений шар дозволів на роботи. Масове додавання плиток, AI без надійного джерела та поспішне підключення платежів дадуть більше ризику, ніж ефекту.

## 2. Що саме перевірено

### Середовище й межі

- Переглянуто README, конфігурації, попередні аудити й документи підготовки, поточні критичні мобільні та серверні реалізації, сховища, декодери, навігацію, редактор і наявні перевірки. Файлів AGENTS.md у перевірених місцях не знайдено. Це не формальна перевірка кожного рядка репозиторію.
- `npm run release:check` виконано повністю, успішно.
- Бекенд перевірено **офлайн, з уже встановленим Maven і кешем залежностей користувача**: 38 тестів, 0 failures, 0 errors, 1 skipped; 37 виконалися. Пропущений тест — опційна жива перевірка постачальника світла.
- Звичайний `mvnw.cmd` спочатку не зміг завантажити дистрибутив у sandbox. Це обмеження стартового шляху середовища; остаточний успішний запуск використав наявний кеш, без встановлення нових залежностей.
- Запущено окремий Spring Boot на `127.0.0.1:8095`, з H2 **у пам’яті**, тестовими міграціями, вимкненим плановим імпортом і push. Імпорт GTFS виконувався лише в цю тимчасову БД.
- Робочий PostgreSQL, особисті акаунти, звичайний `.env`, ключі погоди/тривоги й редакторський контент не використовувалися для змін. У дослідному сервері імпорт `.env` вимкнено, ключі провайдерів навмисно порожні.
- У браузері відкрито поточний App через окремий локальний сервер. Він передавав GET-запити до дослідного бекенду й блокував інші HTTP-методи. Тому новини, транспорт, безбар’єрність та інші відповіді цього проходу були реальними, а робочі серверні дані залишалися недоторканими.
- Окремо коротко використано наявний preview із синтетичними відповідями. Його результати не зараховано як підтвердження живих інтеграцій. Початкова помилка worker у цьому preview була проблемою його обслуговування `/vendor/`, а не підтвердженим дефектом основної карти паркування.
- Додано локальну тестову сесію паркування й приклад запису ЦНАП у дослідному браузерному origin. Попередні налаштування не очищалися. Тимчасове перемикання мови/теми повернуто до початкових української й темної теми.
- **Не перевірено на фізичному телефоні:** нативні карти, камера, дозволи, системна клавіатура, жести, VoiceOver/TalkBack, найбільший системний шрифт, довгі історії SecureStore, встановлення підписаної збірки. Браузерна ширина 320 px не замінює ці перевірки.

Умови стандартних тайлів вимагають коректної ідентифікації/Referer і не гарантують доступність: [політика OSMF](https://operations.osmfoundation.org/policies/tiles/).

**Готово, коли:** на реальному браузері/телефоні й мережі показу карта відкривається після холодного старту та повернення, маршрут і автобуси читабельні; за недоступності провайдера є охайна схема/список без плиток блокування. Нативну карту тестувати окремо.

**Відтворення:** GET `/api/city-services/open-data/datasets` на дослідному сервері. Результат 503, причина upstream — 400 `Invalid "sort" parameter`. Прямий URL `package_search?sort=metadata_modified%20desc&rows=1` повертає 200 і 72 набори. Варіант із `%2520` повертає саме 400 з такою помилкою.

### Зовнішні ризики, які не слід видавати за доведені помилки застосунку

- **Час джерела світла:** о 14:55 UTC дослідний адаптер отримав `sourceUpdatedAt=17:54:02Z`, майже на три години в майбутньому. Код правильно виставив `stale=true`. Для адреси ЦНАП також `addressKnown=false`. Ймовірний часовий дефект джерела потребує підтвердження; не віднімати три години без контракту й не перетворювати невизначеність на «світло є».
- **Погода/тривога з ключами:** у дослідному середовищі ключі навмисно порожні. Це перевірка негативних станів, а не доказ, що ключів немає у власника або що його сервер неправильно налаштовано.
- **Розмір native-сховища:** до 50 паркувань із продовженнями зберігаються одним JSON у SecureStore; квитки/адреси/ЦНАП також там. Збою на iPhone не відтворено, але довгі історії слід винести у придатне локальне сховище до пілота. Мінімальні секрети залишити в SecureStore. [Реалізація](/C:/Users/bahen/IdeaProjects/uzhhorod-app/mobile/src/storage/parkingSessions.ts:18).
- **Залежності:** свіжий read-only `npm audit` — 23 записи: 16 high, 7 moderate, 0 critical. Це не 23 підтверджені атаки на застосунок. Потрібен розбір reachable paths і розподіл tooling/runtime; автоматичне `fix --force` пропонує небажані великі зміни/старі версії SDK і перед презентацією не підходить.
- **Акаунти:** сервер не має окремих інтеграційних тестів повного lifecycle акаунта в поточному наборі. Одна сесія на користувача, немає відновлення/верифікації пошти; перевірка унікальності email перед save не гарантує коректного 409 при конкурентній реєстрації. Для пілота потрібна перевірка цих шляхів і обмеження запитів.
- **Публічний реліз:** у `app.json` немає налаштованих видавничих package/bundle identifiers; політика приватності містить поля для назви, дати й контакту. Це конкретні незавершені кроки публікації, не причина відкладати закриту презентацію. [Політика](/C:/Users/bahen/IdeaProjects/uzhhorod-app/LEGAL/PRIVACY_POLICY_UK.md:5).

## 6. Відкриті дані: що реально доступно зараз

### Метод і важливе розрізнення

20.10 виконано прямі GET-запити до CKAN API, datastore та GeoJSON. Каталог міста повернув **72 набори**; запит до data.gov.ua з фільтром організації `uzhhorodska-miska-rada` — **55**. Це окремі каталоги/вибірки, не гарантовані однакові дзеркала.

Пошукові копії вебсторінок містять інші UUID і попередні стани модерації, ніж поточний API. Тому наведені нижче числа ресурсів — за реальною відповіддю API, а не за описом пошуку. Старі посилання з застосунку повернули HTTP 200; їх не позначаю зламаними лише через відмінність UUID.

Оновлення `metadata_modified` у жовтні не доводить появи нових фактичних записів. Наприклад, моніторинги доступності датовані **15.05.2023–07.03.2024**, хоча метадані набору змінені сьогодні.

### A. «Мій маршрут»: завершений щоденний сценарій

**20–30 секунд показу:** на головній видно обраний №7 → одне натискання → напрямок, позиції автобусів, вибір зупинки й планові відправлення. Глядач одразу розуміє причину повертатися в застосунок.

Мінімальний обсяг: одна картка для наявного обраного маршруту; нейтральний стан без обраного; та сама перевірена карта без дублювання транспортної логіки. Для акаунта використати вже наявні favorites; окрему гостьову синхронізацію не обіцяти. Без мережі відкрити позначений кеш каталогу, а GPS приховати як неактуальний. Не показувати вигадане «автобус за 2 хв».

Критерій готовності: холодний/повторний старт, 0/1 обраний маршрут, source unavailable і повернення не дають тупика. Це полірування наявної функції з вищою цінністю, ніж ще одна плитка.

### B. Мініпрогулянка: невеликий місцевий «прикол» із користю

**20–30 секунд показу:** «Прогулянка набережною» → 5 уже перевірених локацій → деталь і координати → вручну «Відвідано» → прогрес 1/5. Після завершення — стримане досягнення на кшталт «Знайомлюся з Ужгородом».

Мінімальний обсяг: одна кураторська добірка з наявних 21 записів, локальне збереження прогресу, початок/продовження, явний ручний check-in. Без автоматичного стеження за місцем, QR-інфраструктури, рейтингів і випадкових призів. Геометрія між точками не повинна видаватися за перевірений пішохідний маршрут; справжнє прокладання можна делегувати зовнішній карті.

Без мережі список і прогрес доступні локально, якщо їх заздалегідь збережено; підкладку не називати офлайн-картою. Залежність — звірити вибрані п’ять локацій, а не перевіряти весь каталог заново заради однієї прогулянки.

### C. Карта дозволів: видима інтеграція міських даних

**20–30 секунд показу:** обрати шар «Дозволи на роботи» → натиснути точку → побачити тип робіт, адресу, статус дозволу, час отримання даних і першоджерело.

Мінімальний обсяг: один серверний адаптер і нормалізований DTO, дедуплікація за ID, перевірка координат, кеш зі stale, список як альтернатива карті, простий фільтр. Не переносити зайві персональні поля заявників. Не називати шар «Перекриття зараз»: дозвіл і реальний стан вулиці — різні факти.

Без мережі — попередня позначена копія, без твердження про поточні роботи. Після помилки першого завантаження — ясна відмова та посилання на джерело. Залежності: стабільна підкладка, атрибуція CC BY 4.0, перевірка семантики статусу. На тижневому горизонті це сильніше, ніж починати платіжну інтеграцію.

### Якщо є 1 день

Бюджет — приблизно 8 годин. 3 год на карту показу, 2 год на парсер безбар’єрності, 1 год на читач новин, 1 год на актуалізацію контенту, 1 год на репетицію телефона й запис резервного відео. Якщо карта потребує більше часу — скоротити перелік екранів; не починати нові фічі. Корекцію основної кнопки ЦНАП взяти лише за наявності часу або пропустити ЦНАП у головному показі.

«Вау» цього дня — реальні автобуси, читання актуальної новини та активна сесія паркування, яка відновлюється після перезапуску. Усе це вже реалізовано.

### Якщо є 3 дні

Бюджет — приблизно 24 години сумарно. Після одноденного пакета: 4 год на ієрархію головної/швидкий маршрут, близько 8 год на мінімальну прогулянку, до 2 год на ЦНАП і ARIA, решта — негативні стани й репетиція. Якщо задача вийшла за нижню оцінку, прогулянку зменшити до однієї добірки без нової карти. Нові міські інтеграції ще не обов’язкові.

### Якщо є 7 днів

Бюджет — приблизно 56 годин сумарно. До триденного пакета додати 12–20 год на шар дозволів, 6–8 год на деталі доступності за умови підтвердження даних, 6–8 год на регресію, пристрої й доведення контенту. Залишити буфер, а не обіцяти весь верхній діапазон оцінок одночасно. Останню добу — без нових інтеграцій.

### Що відкласти

Справжні платежі й облік у паркувального оператора; офіційне голосування; персональні штрафи; екстрені push без перевіреної доставки; AI, що відповідає про укриття чи відключення без надійних джерел; повне переписування App.tsx і навігації; масове оновлення SDK перед зустріччю; карти для наборів із нульовими ресурсами. Це окремі проєктні етапи, а не дрібний «підключити API».

### Підготовлений стан

Одна відрепетирувана збірка, перевірений маршрут і час його роботи, завантажений каталог, охайна історія без особистих даних, тестовий номер авто, готовий тестовий спосіб оплати, кілька актуальних подій. Акаунт — лише окремий демонстраційний за потреби; гостьового сценарію достатньо. Ключ редактора не повинен з’являтися в дзеркаленні екрана.

### За добу

- Виконати наявні перевірки після виправлень; не вважати їх заміною телефона.
- На тому самому телефоні пройти показ двічі з холодного старту, у світлій/темній темі, перевірити великий шрифт, системний Back/жест, клавіатуру й дозволи камери, якщо QR входить у сценарій.
- Перевірити підкладку саме в браузері/збірці показу, а не лише endpoint GPS.
- Звірити джерела й дату подій; для погоди/тривоги перевірити власну налаштовану конфігурацію окремо від цього аудиту.
- Перевірити доступ телефона до API через власний хот-спот. Expo tunnel не робить backend автоматично доступним.
- Записати 3 короткі відеофрагменти: транспорт 30–45 с, завершене паркування/відновлення 30–45 с, новина/подія або ЦНАП 20–30 с. Це рекомендація для запису з реального телефона; відео в цьому аудиті не створювалося.

### За 15 хвилин

- Телефон заряджений, потрібна збірка відкрита, трансляція екрана працює, шрифт і орієнтація перевірені.
- API доступний, транспорт імпортований, обраний маршрут щойно перевірено на наявність позицій.
- На карті справжня підкладка, а не Access blocked; зупинка й планові рейси відкриваються.
- Новина й подія актуальні; немає нескінченного спінера або випадкового старого тестового стану.
- Резервне відео відкривається без мережі. Доповідач знає, який сценарій пропускає при відмові джерела.

### Якщо щось відмовило

**Немає GPS:** сказати, що джерело зараз не надало позицій, показати GTFS-каталог і плановий розклад. Не рухати автобуси штучно.

**Немає мережі:** показати позначений кеш транспорту та локальну сесію паркування; для повного сценарію перейти до заздалегідь записаного відео й назвати його записом. Повний розклад/стаття/тайли не гарантовано доступні офлайн.

**Немає погоди/статусу тривоги:** залишити чесний недоступний стан і перейти до основної задачі. Не створювати демонстраційний «відбій» у звичайному режимі.

**Немає API:** використовувати локальні сценарії та резерв. Наявний synthetic preview підходить для QA, але його не можна представляти як поточні реальні міські дані.
